# Research — Competitors

One file per competitor, dated: `YYYY-MM-DD-<competitor>.md`.

## Purpose

**To find what they get wrong, not to learn what to copy.**

A competitor analysis that concludes "we should do what they do" has produced a second
version of an existing product. The valuable output is the specific place where a
competitor's design fails their user — because that's where FollowUp can be better in a
way that's hard to reverse.

## What to capture

- **Who it's for** and how that differs from FollowUp's owner persona
- **The core loop** — what the user does most often, and how many steps it takes
- **Where the design makes the user do work the software should do**
- **Trust posture** — how they present automation, permission, and control. Critical for
  this category: several competitors present aggressive automation as a feature.
- **What they do genuinely well** (be honest — dismissing competitors makes you worse)
- **The specific gap FollowUp could own**
- **Evidence quality** — did you use the product, see a demo, or read a marketing page?
  Marketing pages lie; say which you had.

## Rules

1. **Never copy a competitor's interface.** Same rule as references, more strictly —
   proximity makes plagiarism both easier and more damaging.
2. **Don't design in reaction.** "They have it, so we need it" is how a focused product
   becomes a feature checklist. See rule 4 in `followup/PRODUCT_DIRECTION.md`.
3. **Separate what you saw from what you assume.** You usually can't see their
   authenticated product. Say so rather than describing it from imagination.
4. **Marketing screenshots are not the product.** They're idealized, often mocked up.
