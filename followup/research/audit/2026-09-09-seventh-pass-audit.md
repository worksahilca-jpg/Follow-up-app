## Findings

### 1. The Twilio signature-failure monitor leaks the business's live Twilio secret straight into Sentry, via a field the app's own PII scrubber never touches

- **Where:** `src/lib/twilio.ts:74-83` (`validateTwilioRequestSignature`) — the `recordAuthFailure("twilio_signature", { path: new URL(request.url).pathname })` call on line 81 — called from every Twilio-secret-keyed route: `src/app/api/twilio/sms/[secret]/route.ts:47`, `.../voice/[secret]/route.ts:97`, `.../voice/transcription/[secret]/route.ts:40`, `.../whatsapp/[secret]/route.ts:54`. The receiving function, `recordAuthFailure()` (`src/lib/monitoring.ts:32-43`), forwards its `context` object verbatim as `extra` on a `Sentry.captureMessage()` call. `beforeSend()` (`src/lib/sentryScrub.ts:34-79`) — the one place this app scrubs outgoing Sentry events — only ever touches `event.message`, `event.exception[].value`, `event.breadcrumbs`, a fixed allowlist of `event.request` subfields (`data`/`cookies`/`query_string`/`headers`), and `event.user`. It never looks at `event.extra` at all.
- **Bug:** Every one of these four routes is reached at a URL shaped `/api/twilio/{sms,voice,whatsapp,voice/transcription}/[secret]`, where `[secret]` is the literal, live `Business.twilioSecret` value used to route the inbound webhook to the right tenant (`findBusinessByTwilioSecret()`, looked up *before* signature validation runs). When Twilio's `X-Twilio-Signature` fails to validate — which the file's own comments say can happen even for **genuine** Twilio traffic, not just an attacker, due to "proxy/protocol rewriting... a known, silent source of signature-validation failures elsewhere" (`src/lib/twilio.ts:40-46`) — `recordAuthFailure` fires with `path` set to `new URL(request.url).pathname`, i.e. the full path **including the raw secret segment**. This lands in Sentry as `extra.path` on a `security_alert: true`-tagged event, completely bypassing every scrub `beforeSend` performs, because `beforeSend` was never written to look at `extra`. The project's own test suite (`src/lib/__tests__/sentryScrub.test.ts`) confirms the gap by omission: it explicitly tests that `request.query_string`/`cookies`/`data` get stripped, but has no test at all for `event.extra`.
- **Concrete failure scenario:** A business's Twilio Auth Token is rotated in the Twilio console but not yet re-saved in FollowUp Settings (an ordinary, realistic drift — nothing enforces the two stay in sync), or the app is simply reached via a alternate host header the code doesn't yet special-case (the exact class of false-positive the file's own comments describe as already having happened once for "apex vs www"). The very next real inbound SMS/call/WhatsApp message for that business fails signature validation, and `recordAuthFailure` immediately ships that business's live `twilioSecret` — the one credential that authorizes anyone to POST fabricated inbound messages/calls into that business's lead pipeline (see pass-1 finding #1's threat model) — to Sentry as plain, unscrubbed `extra` data. Anyone with read access to the Sentry project (a teammate, a support contractor, or an attacker who separately compromises the Sentry account) now has a live secret usable to inject fake leads/messages into that business's pipeline, entirely independent of any application-level bug.
- **Suggested fix:** Either stop putting the raw path in `extra` (log a coarse route name like the `webhook_secret` failure case already does — `recordAuthFailure("webhook_secret", { route: "webhooks/lead" })` never includes the secret) or extend `beforeSend` to scrub `event.extra` (and any other free-form context bag) through the same `scrubPii`/secret-aware treatment applied to breadcrumb `data`. The safest fix is at the call site: pass a redacted route label, not the literal request path, since the path segment is by construction a live credential for every Twilio-secret route in this app.

### 2. Next.js's own automatic error-forwarding attaches the full, unscrubbed request path (including any query-string secret) to every uncaught route-handler exception — a second, broader path into Sentry that `beforeSend` was never built to cover

- **Where:** `src/instrumentation.ts:26-29` (`onRequestError`, wired per Next's own convention to fire for "a Server Component render, a Route Handler, a Server Action" on *any* uncaught exception, per the file's own comment) → `@sentry/nextjs`'s `captureRequestError()` (`node_modules/@sentry/nextjs/build/cjs/common/captureRequestError.js:6-29`), which does `scope.setContext("nextjs", { request_path: request.path, ... })` → Next's own `base-server.js:472` sets that `request.path` to the raw, un-normalized `req.url` (`path: req.url || ''`), which for a Node `IncomingMessage` is the path **plus its full query string**, not just the pathname.
- **Bug:** `beforeSend()` in `src/lib/sentryScrub.ts` never inspects `event.contexts` at all — only `message`/`exception`/`breadcrumbs`/`request`/`user`. So for *any* uncaught exception thrown inside a route handler whose URL carries a secret — every `[secret]`-path Twilio/webhook route (same four as finding #1, plus `src/app/api/webhooks/lead/[secret]/route.ts` and `src/app/api/twilio/voice-agent-callback|voice-agent-auth/[secret]/route.ts`), or `src/app/api/integrations/gmail/push/route.ts`, which is authenticated via a raw `?secret=GMAIL_PUSH_SECRET` query parameter (confirmed in the fifth-pass audit) — the literal secret reaches Sentry verbatim as `event.contexts.nextjs.request_path`, independent of and in addition to the `event.request.query_string` field `beforeSend` does correctly strip. This is a different, wider vector than finding #1: it fires on *any* unhandled bug in *any* of these routes (a Prisma error, a malformed-body `TypeError`, a null-ref on unexpected input), not only on a signature mismatch.
- **Concrete failure scenario:** A transient Prisma connection error, or any other not-explicitly-caught exception, occurs while handling a request to `GET /api/integrations/gmail/push?secret=<GMAIL_PUSH_SECRET>` or `POST /api/twilio/sms/<twilioSecret>`. Next.js's instrumentation hook fires automatically (this is exactly what `instrumentation.ts` exists to guarantee happens for every such error), attaches `request_path` with the full, unmodified URL including the secret, and ships it to Sentry. `GMAIL_PUSH_SECRET` is a single shared secret across the whole app (per the fifth-pass audit's description) — a single leak of it via one business's transient error would let an attacker forge Gmail push notifications for *any* business's mailbox, not just the one that happened to error.
- **Suggested fix:** Add `event.contexts` (and any other free-form bag Sentry populates automatically — `extra`, `contexts.nextjs`) to what `beforeSend` scrubs: at minimum, strip or path-only-normalize `event.contexts?.nextjs?.request_path` the same way `event.request.query_string` is already deleted, since the underlying value is the same raw request URL with the same secret-in-path/query risk. A regex-based `scrubPii`-style pass over every string value in `event.contexts` before it's asserted safe would close both this and finding #1's `extra.path` gap in one place.

## Areas checked and found clean

- **Analytics/insights tenant isolation** (`src/lib/analytics-data.ts`, `getAnalytics()`): every one of the five parallel top-level queries (`lead.findMany`, `followUp.findMany`, `user.findMany`, and both `lead.count` calls) filters directly on `businessId: ctx.businessId`, and the one query that joins across tables — `followUp.findMany({ where: { ..., lead: { businessId: ctx.businessId } } })` — re-asserts the businessId filter at the join level exactly as the brief warned to check for, rather than trusting an already-scoped `leadId` list. The team-breakdown sub-query (`assignedLeads`) double-scopes: both `businessId` directly *and* `assignedToId: { in: userIds }` where `userIds` itself comes from a businessId-scoped `user.findMany` moments earlier — no path was found where a cross-tenant id could leak in. There is no separate API route for this page (`src/app/(app)/analytics/page.tsx` calls `getAnalytics()` directly as a server component, and `AnalyticsCharts`/`TeamPerformanceSection` are pure presentational components with no client-side fetch of their own), so there's no separate route-level surface to re-check independently.
- **Weekly digest cross-tenant leakage** (`src/lib/rescued.ts` `getRescueReport()`, `src/app/api/cron/weekly-digest/route.ts`): `getRescueReport(businessId, days)` scopes every query to that one `businessId` (`followUp.findMany({ where: { ..., lead: { businessId } } })`, and the `booking.count` re-asserts `businessId` again alongside the already-derived `leadId: { in: rescuedIds }`, so a lead id could never cross a tenant boundary even redundantly). The cron route builds one `report` per business inside a per-business closure and sends it only to that same business's `b.users` (an admin list fetched as a *nested* Prisma relation select scoped to that business, not a second free-standing query — so there is no code path where two businesses' user lists could be concatenated into one send). Recipient staleness was checked specifically per the brief's question: `removeMember()` (from earlier passes) nulls out `User.businessId` on removal, which drops that user out of the nested `users` relation on the *next* cron run — there is no cached/stale email list anywhere in this path, since the recipient list is queried fresh on every invocation, not stored. `sendEmail()` sends from the business's own connected Gmail integration (`getGmailIntegration`, scoped `where: { provider: "gmail", status: "connected", user: { businessId } }`), so the "From" address is also correctly tenant-bound.
- **De-identification pipeline correctness** (`src/lib/deidentify.ts`, `buildDeidentifiedTrainingSet()`): the opt-in gate matches `docs/security-roadmap.md` exactly and is genuinely enforced first — `Business.allowModelTraining` defaults to `false` in the schema and migration, is never set anywhere in the codebase (no settings route, no seed script exposes a way to flip it), and `buildDeidentifiedTrainingSet()` checks it before issuing a single `lead.findMany` (verified by the negative-path test asserting `prisma.lead.findMany` is never called when the flag is off). The function itself is not wired into anything yet — no route or cron calls it — matching the roadmap doc's own "not built yet" note, so there's no live path where the gate could be bypassed today. On the substance of the de-identification itself: name/email/phone/company are matched structurally (not just verbatim — `phoneDigitsPattern()` fuzzy-matches a stored phone number regardless of how it's reformatted in free text), and the generic backstop's broad `PHONE_RE` (`/(\+?\d[\d\s().-]{6,}\d)/g`, shared with `sentryScrub.ts`) is loose enough that it incidentally also catches SSN/SIN-shaped digit runs (e.g. `123-45-6789` or a bare 9-digit SIN) as a side effect of matching "any long digit run with optional separators," even though nothing in this file specifically targets government ID numbers — so the specific PII shapes named in the brief (name, email, phone, and a digit-based ID mentioned in conversation) are, in practice, covered. The real, already-self-disclosed gap (`Lead.notes`, `scoreReason`, `AIInsight.summary` not covered; the address regex is a best-effort heuristic that can miss non-US formats) is documented in both the file's own header comment and `docs/security-roadmap.md` rule 2 as known and deliberately out of scope for this pass, not a hidden defect — so it is not re-reported here as a new finding.
- **Ponds (shared claimable lead pool) API routes** (`src/app/api/leads/[id]/claim/route.ts`, `src/app/api/leads/[id]/assign/route.ts`): both routes re-derive `businessId` from `getSessionContext()` (never from the client) and pass it into the corresponding `src/lib/assignment.ts` function, which independently re-checks `lead.businessId !== businessId` before doing anything. The claim route in particular calls `claimLead()`, which performs the atomic conditional `updateMany({ where: { id: leadId, assignedToId: null }, data: { assignedToId: userId } })` **at the route level**, not just inside a lib function that could theoretically be bypassed — there is no second code path that can set `assignedToId` directly (the general lead-update route, `src/app/api/leads/[id]/route.ts`, does not accept `assignedToId` in its body at all, confirmed by grep), so the only two ways to change assignment are the atomic claim and the always-overwriting `assign` (deliberately non-atomic, by design, for manual reassignment). No cross-tenant or race-condition gap found beyond what pass 1 already verified.

## Summary

Two findings, both in the Sentry/error-monitoring area, both concrete and confirmed by reading both the application code and the relevant `@sentry/core`/`@sentry/nextjs`/Next.js library internals rather than assumed from the config's own comments. Finding #1 is the more serious and the more directly reachable: an explicit, deliberate line of application code (`recordAuthFailure("twilio_signature", { path: ... })`) puts a live, still-valid tenant secret into a Sentry event field the scrubber does not cover, and it fires on a condition the code's own comments admit can happen to genuine traffic, not only an attacker. Finding #2 is the same root cause (the scrubber's allowlist-of-fields approach misses `extra`/`contexts`) reached via a different, broader trigger — any uncaught exception in any secret-bearing route, via Next's own automatic instrumentation rather than application code.

Analytics tenant isolation, weekly digest recipient/content isolation, the de-identification pipeline's opt-in gate and PII coverage, and the Ponds claim/assign routes were all read in full on both sides of their respective interactions and came back clean — see the "checked and clean" section above for the specific reasoning behind each rather than a bare assertion.
