## P2 — MEDIUM — Both halves of the fix assume three Meta ids are equal, and nothing has verified that

**Grade:** PLAUSIBLE.

**Where the ids come from:**
- `sending.ts:617`: the Send API `message_id` becomes `externalId`.
- `instagramPoll.ts:110`: the Conversations API `id` becomes `mid`.
- `meta.ts:307`: the webhook `mid`.
- `instagram.ts:520-524`: the upsert on `externalId`.

The tests use one `MID` constant for both the send and the read-back (`instagramOwnSendRoundTrip.test.ts:105, 116, 154`). They pin the assumption; they don't verify it.

**Failure scenarios:**
- **Send id ≠ Conversations id.** After the backfill, every FollowUp send is captured a second time as "Sent directly on Instagram — not through FollowUp". F2 stays unfixed. That is no worse than today.
- **Webhook `mid` ≠ Conversations id.** This one is new with this PR, because the backfill is what first makes webhooks route. Once Meta delivers webhooks, every inbound DM is stored twice and scored and drafted twice. That doubles OpenAI spend and the thread. The ack is once per lead (`acknowledge.ts:551-555`), so there is no double send. Meta delivers no DM webhooks today (09-24 audit, Q3), so this is latent.

**Smallest fix (no code):** after the first post-backfill send from the founder business, run:

```sql
SELECT m.direction, m.source, m.trigger, m."externalId", m."sentAt", md5(m.body) AS body_hash
FROM "Message" m JOIN "Conversation" c ON c.id = m."conversationId" JOIN "Lead" l ON l.id = c."leadId"
WHERE l."businessId" = 'cmtibjn400000iq84yxpzsw45' AND c.channel = 'instagram'
  AND m."sentAt" > now() - interval '30 minutes'
ORDER BY m."sentAt";
```

- **Pass:** one outbound row, with `source` NULL and a non-null `externalId`.
- **Fail:** two rows with the same `body_hash`. The ids differ. Give the audit's body-and-time fallback to backend-ai-agent.

Repeat the check for one inbound DM once webhooks arrive.

## P3 — MEDIUM (only if migrate fails) — A failed migrate doesn't stop the deploy, and this code can't run without the column

**Grade:** CONFIRMED in code (`package.json:7`). The outage itself is PLAUSIBLE, and only if migrate fails.

`"build": "(prisma migrate deploy || echo 'WARNING …') && next build"` carries on building when migrate fails.

The generated client knows `instagramAccountId`. Without the column, P2022 hits:
- every Business read that has no `select`
- every one of the 28 `prisma.business.update/upsert/create` call sites that has no `select`, because Prisma returns the whole row

That includes:
- the poll's `findMany`, which selects the new column (`instagramPoll.ts:249`), and its cursor write (`:237`)
- webhook routing (`meta.ts:257-259`)
- both connect paths

**Effect:** no DM arrives by either path, no connect succeeds, and most settings saves fail.

**The migration itself is safe:**
- A nullable `ADD COLUMN` is metadata-only.
- A unique index over all-NULL values can't fail, because NULLs are distinct.
- Business has only a few rows, so the locks last moments.
- Rolling back is safe, because the old code ignores the column.

**Smallest fix:** immediately after deploy, run:

```sql
SELECT finished_at, rolled_back_at FROM _prisma_migrations
WHERE migration_name = '20260925010000_instagram_account_id';
```

Expect `finished_at` to be set. If Preview deployments share the production database, the PR's preview build has already applied the migration.

Removing the `|| echo` is a separate, pre-existing issue for backend-ai-agent.

## P4 — LOW — Uniqueness is checked per column, so one Instagram account can end up on two businesses

**Grade:** PLAUSIBLE. It gives no one access they didn't already have.

**Where:**
- two separate `@unique` in `schema.prisma`
- `config/route.ts:98-115`
- `callback/route.ts:61-72`
- `instagramAccountBackfill.ts:101`

**Scenario:**
1. Before the backfill, business X has `instagramAccountId` NULL.
2. Someone who can log in to X's Instagram account pastes a token from a *different* Meta app into business Y.
3. That app gives a different app-scoped id, so `instagramUserId` doesn't clash. The 1784… id clashes with nothing, because X's column is still NULL.
4. The save succeeds. Both pollers now ingest the account, and webhooks route to Y.

The backfill then reports `already_attached` for X, which is correct.

Doing this needs a valid token for the account. OAuth through the same app is still refused, because the app-scoped id clashes.

**Smallest fix:** as a backstop in both connect paths and in the backfill's holder check, refuse the save when another business holds either resolved id in either column:

```ts
findFirst({ where: { id: { not: businessId }, OR: [{ instagramUserId: { in: ids } }, { instagramAccountId: { in: ids } }] } })
```

## P5 — LOW — A 400 on `user_id` during a reconnect silently clears a good `instagramAccountId`

**Grade:** PLAUSIBLE.
**Where:** `instagram.ts:164-170` → `config/route.ts:107`, `callback/route.ts:68`.

**Scenario:**
1. A business that has been backfilled reconnects the same account.
2. The first `/me` returns a 400. The fallback can't tell "unknown field" apart from any other 400.
3. The retry succeeds, but without `user_id`. The code writes NULL.

The only trace is one `console.error`. Webhooks stop routing and the phantom self-lead comes back.

**Smallest fix:** if `!resolved.accountId && resolved.id === stored instagramUserId`, don't write `instagramAccountId`. It is the same account, so the stored value is still correct.

The same 400 blanks the diagnose account panel, because `instagramDiagnostics` (`instagram.ts:267`) asks for `user_id` with no fallback. That affects diagnostics only.

## Checked, clean

- **Tenant isolation of routing.**
  - `entry.id` comes only from Meta-signed envelopes, or from the business's own stored id (the poller).
  - Each of the two lookups is unique (`meta.ts:257-259`).
  - Storing another account's id requires a token for that account. P4 is the only variant.
- **The claim in `sending.ts`.**
  - It updates `where: { externalId, direction: "outbound", conversation: { leadId: lead.id } }` (`:842-845`).
  - `externalId` is globally unique, so that is at most one row, and only one belonging to this lead.
  - A clash with another tenant's row rethrows, as before.
  - Every throw lands inside the post-send `try`, so nothing is retried or sent twice.
- **The own-sender rule.**
  - `ownIds` holds only the processing business's own ids (`meta.ts:264`, `instagramPoll.ts:171`).
  - A customer's IGSID is never one of them, even when another FollowUp business is the one sending the DM.
  - Events with no message content are skipped first (`:269`), and own→own messages are dropped (`:292`).
  - No real customer message is swallowed.
- **`resolveInstagramUserId`.**
  - A non-400 error behaves as before. A 400 retries with the old fields.
  - The id is taken from the raw digits if Meta ever sends a number. Anything that isn't all digits is refused (`instagram.ts:229-237`).
  - It can't cost a working connect.
- **Writes of the new column.**
  - Both connect paths write it in the same update as the token and `instagramUserId`, and disconnect clears it (`config/route.ts:98-115, 177-186`, `callback/route.ts:61-72`).
  - Nothing else writes or clears these columns (grep).
- **Backfill defaults.**
  - Dry run is the default. It only reads rows where the value is NULL.
  - The write is conditional on the value still being NULL and `instagramUserId` being unchanged (`instagramAccountBackfill.ts:114`).
  - It refuses `different_account` and `already_attached`. Any outcome other than fill exits 1.
  - It can't overwrite a value or attach one account to two businesses.
- **Secrets.**
  - No new log line or error string carries a token. Resolve errors are Meta's own sentence (`instagram.ts:191, 605-615`).
  - Prisma's own `log: ["error"]` (`db.ts:55`) prints Prisma errors whether or not the script suppresses them. In my run that printed only `127.0.0.1:1`, the host and port. No backfill query argument contains a token.
